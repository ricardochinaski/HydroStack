1. ARQUITECTURA DE DATOS E IoT EN FLUTTER

1.1 Estrategia de Sincronización Realtime

Problema actual: No existe conexión real con el ESP32. Cuando llegue, los sensores de pH (GPIO34) y EC (GPIO35) emitirán lecturas analógicas cada ~200ms. Persistir cada lectura individual en Firebase RTDB o MQTT saturará la red, quemará ancho de banda y congelará la UI con rebuilds innecesarios.

Solución: Pipeline de 3 capas

ESP32 ADC (200ms) │ ▼ [Throttle 1s] ←── firmware: publicar cada 1s máximo │ ▼ MQTT Broker / Firebase RTDB │ ▼ Flutter StreamSubscription │ ▼ [Debounce 500ms + Distinct by deadband] │ ▼ Riverpod StreamProvider<SensorLectura> │ ▼ UI (ConsumerWidget)

Lógica de deadband (histéresis)

Ignorar variaciones menores a 0.05 en pH y 0.02 en EC para evitar ruido eléctrico del ADC:

bool _withinDeadband(SensorLectura a, SensorLectura b) {
  return (a.ph - b.ph).abs() < 0.05 &&
         (a.ec - b.ec).abs() < 0.02;
}

final sensorTelemetryProvider = StreamProvider<SensorLectura>((ref) {
  return _esp32Stream
    .throttle(const Duration(seconds: 1))
    .debounce(const Duration(milliseconds: 500))
    .distinct(_withinDeadband)
    .asyncMap(_calibrate);
});

Throttling del lado del ESP32 (firmware)

unsigned long lastPublish = 0;
void loop() {
  if (millis() - lastPublish >= 1000) {
    float ph = analogRead(34) * (3.3 / 4095.0);
    float ec = analogRead(35) * (3.3 / 4095.0);
    client.publish("hidrosmart/sensores", serialize(ph, ec));
    lastPublish = millis();
  }
}

Command Queue Service (código conceptual)

class CommandQueueService {
  final LocalDb _db;
  final MqttService _mqtt;

  Future<void> enqueue(ActuatorCommand cmd) async {
    await _db.insertPending(cmd);
    try {
      await _mqtt.publish(cmd.topic, cmd.payload);
      await _db.markSynced(cmd.id);
    } on SocketException {
      // queda en pending, se reintenta en próximo ciclo
    }
  }

  Future<void> flushPending() async {
    for (final cmd in await _db.getPending()) {
      await _mqtt.publish(cmd.topic, cmd.payload);
      await _db.markSynced(cmd.id);
    }
  }
}

1.3 Gestión de Estado (Riverpod vs BLoC)

Recomendación: Mantener Riverpod. Es superior para este caso por 3 razones:

  1. StreamProvider nativo — Engancha directo al stream de Firebase/MQTT sin el boilerplate BLoC (Event → State → Bloc → UI).
  2. .family modifiers — Cada planta/sensor puede tener su propio provider parametrizado sin instanciar N Blocs.
  3. ref.invalidate() — Para forzar recarga de catálogo, comandos, etc., sin reinjectar dependencias.

Efecto deseado: El usuario toca "Activar modo PRO" y el dashboard hace una transición fluida donde las tarjetas se "expanden" para revelar nueva telemetría.

class ModeTransitionDashboard extends ConsumerWidget {
  @override
  Widget build(BuildContext context, WidgetRef ref) {
    final mode = ref.watch(userModeProvider);
    return AnimatedSwitcher(
      duration: const Duration(milliseconds: 500),
      switchInCurve: Curves.easeOutCubic,
      child: _buildForMode(mode, key: ValueKey(mode)),
    );
  }

  Widget _buildForMode(AppMode mode, {Key? key}) {
    switch (mode) {
      case AppMode.eco:        return _EcoDashboard(key: key);
      case AppMode.autonomo:   return _AutonomoDashboard(key: key);
      case AppMode.pro:        return _ProDashboard(key: key);
    }
  }
}
Lado firmware ESP32

Al cambiar de modo, la app envía un comando MQTT hidrosmart/modo con payload "eco"|"autonomo"|"pro". El ESP32 ajusta los umbrales de los relés en consecuencia (GPIO25, GPIO26, GPIO27).

4. SEGURIDAD, PROVISIONING Y FAIL-SAFE

4.1 Fail-Safe: Pérdida de Comunicación con el ESP32

Lógica temporal (timeouts)

EventoAcción en App
Sin dato de sensor > 10sBanner "SIN SEÑAL" ámbar en cabecera
Sin dato > 30sAlerta push local + ocultar controles de actuadores (modo seguro)
Sin dato > 60sAsumir ESP32 offline — mostrar pantalla de reconexión con tutorial

Watchdog Timer en Flutter

final connectionWatchdogProvider = Provider<Timer>((ref) {
  final timer = Timer.periodic(const Duration(seconds: 10), (_) {
    final lastSeen = ref.read(lastSensorTimestampProvider);
    final delta = DateTime.now().difference(lastSeen);
    if (delta.inSeconds > 30) {
      ref.read(connectionStatusProvider.notifier).state =
          ConnectionStatus.lost;
    } else if (delta.inSeconds > 10) {
      ref.read(connectionStatusProvider.notifier).state =
          ConnectionStatus.unstable;
    }
  });
  ref.onDispose(timer.cancel);
  return timer;
});

4.2 Vinculación Inicial (Device Provisioning)

Recomendación: Usar ESP32 como Access Point + Captive Portal (modo AP) como método primario, con BLE como fallback. Es el estándar de la industria (Philips Hue, Tesla, DJI).

Flujo de provisioning

1. Usuario toca "Vincular ESP32" en app 2. ESP32 inicia en modo AP (Wi-Fi directo "HidroSmart-XXXX") 3. App detecta la red, se conecta automáticamente 4. App envía credenciales Wi-Fi del hogar vía HTTP POST 5. ESP32 se conecta al Wi-Fi del hogar, cierra el AP 6. ESP32 publica "hidrosmart/discover" con su ID único 7. App lo asocia a la cuenta del usuario en Firebase

Código conceptual — provisioning_wizard_screen.dart

Future<void> provisionDevice() async {
  // 1. Escanear redes Wi-Fi
  final networks = await WiFiForIoTPlugin.scan();
  // 2. Conectar a red "HidroSmart-*"
  final hidroNet = networks.firstWhere((n) => n.ssid.startsWith('HidroSmart-'));
  await WiFiForIoTPlugin.connect(hidroNet.ssid);
  // 3. Enviar credenciales vía HTTP
  final response = await http.post(
    Uri.parse('http://192.168.4.1/provision'),
    body: {'ssid': homeSSID, 'password': homePassword},
  );
  // 4. Esperar heartbeat en MQTT
  await mqtt.waitForTopic('hidrosmart/heartbeat', timeout: Duration(seconds: 30));
  // 5. Vincular en Firebase
  await FirebaseDatabase.instance.ref('usuarios/$uid/dispositivos').push({
    'esp32_id': response.body,
    'alias': 'Mi HidroSmart',
    'mode': 'eco',
  });
}

Recomendación final

La app actual tiene una base sólida (estructura de carpetas, sistema de diseño premium, Riverpod, go_router, modelo de datos).

Las dos únicas inversiones críticas antes de cualquier feature nuevo son: (1) offline-first con sqflite y (2) pipeline de throttling en los streams de sensores. Sin ellas, la app no podrá sostener una conexión real con el ESP32 en condiciones domésticas reales (cortes de Wi-Fi, ruido ADC, latencia de red).

Una vez resuelta la capa de comunicación, el modelo FaaS y las microinteracciones premium serán los diferenciadores que justificarán el precio del hardware y la suscripción recurrente.
